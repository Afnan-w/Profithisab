# Data guide (plain English)

This page explains how fund data gets into Profithisab. You do not need to be a
programmer. Most of the time the data arrives **automatically**: a script fetches
NAV histories straight from the asset managers' own websites and the importer
merges them into `/data`. A manual export is still welcome — the importer reads
CSV, JSON or XLSX.

The golden rule: **no number is typed by hand.** Every return, dividend,
drawdown and ranking on the site is calculated from the files in `/data`.
If a file is missing or empty, the site says “Data not available” rather than
inventing a figure.

---

## 1. What is in `/data`

| File or folder | What it holds | Who edits it |
| --- | --- | --- |
| `data/funds.json` | The fund catalogue: name, AMC, type, Shariah flag, fee, size, launch date | Importer (or you, using a template) |
| `data/nav/{slug}.csv` | One NAV per row: `date,nav` | Importer |
| `data/dividends/{slug}.json` | Cash dividend per unit by record date | Importer |
| `data/amcs.json` | Asset manager names and websites | Importer |
| `data/benchmarks.json` | Sanchayapatra, FDR and inflation reference lines, each marked `verified`, `approximate` or `unavailable` | You, with a cited source |
| `data/nav-sources.json` | **The fetch plan**: which sites are fetched, their URLs, politeness rules, and the curated fund list | You, when adding a new source or fund |
| `data/market-roster.json` | Weekly snapshot of every open-end fund in Bangladesh (name, AMC, NAV, AUM) from the LankaBangla portal | The fetcher |
| `data/license.json` | The data-source policy and the exact attribution wording | **You, before the first real import** |
| `data/verification.json` | Named human checks of a fund's data. Empty by default | You, only after a real check |
| `data/review-needed.json` | Suspicious rows waiting for your approval | The importer |
| `data/approved-deviations.json` | Big NAV jumps you have checked and approved | `npm run data:approve` |
| `data/meta.json` | Counts and freshness used by the site | Generated by `data:check` |
| `data/demo/` | The old generated demo dataset, clearly labelled | Nobody; safe to delete now that real data is live |
| `data/incoming/` | Files fetched (or dropped) for the next import | The fetcher, or you |
| `data/templates/` | Copy-and-edit examples for each file | Reference only |

The site only serves `data/demo/` while `data/funds.json` is empty. The moment a
real catalogue exists, the demo files are ignored and the yellow **Demo data**
banner disappears.

## 2. Where the data comes from (the fetch pipeline)

Every source is a **first-party or public disclosure**: each asset management
company publishes its own funds' NAV on its own website, and the LankaBangla
Financial Portal serves a public weekly table of the whole open-end fund
universe. Nothing is scraped from aggregators, and ReturnKoto stays off-limits
without written permission.

`npm run data:fetch` reads `data/nav-sources.json` and:

1. Fetches the LankaBangla open-end table → `data/market-roster.json` (fund
   universe + AUM, converted to crore).
2. Fetches each supported AMC's NAV history → `data/incoming/{source}.json`.
3. Politeness is built in: a clear bot name with a contact address in the
   User-Agent, at least 2.5 seconds between requests, a same-day cache in
   `data/raw/` (never committed), and an instant stop if a server answers
   403 or 429 ("back off").

Supported today: **Shanta AML** (full daily history since inception for its 3
funds, plus dividends) and **IDLC AML** (full available history for its 4
funds; dividend history not yet published by its endpoint). The LankaBangla
roster covers all ~102 open-end funds.

### Adding a new AMC

1. Find the AMC's own NAV page and confirm it is publicly reachable.
2. Add the fund(s) to `data/nav-sources.json` (`funds[]`): slug, name, acronym, AMC
   id, type, Shariah flag, and the source-specific key (fund id or page slug).
3. Teach the fetcher how to read that site (a new adapter in
   `scripts/fetch-nav.ts`) — or, if the site offers a clean download, use the
   manual import in section 4 instead.
4. Run `npm run data:fetch`, then the import steps below.

## 3. Permission policy

No signed permission exists for the current sources because none is required:
the AMCs publish this data publicly and we fetch politely, cache heavily, and
attribute. `data/license.json` records this policy: `permissionDate` is the date
it was adopted (2026-11-11), `permitted[]` lists exactly what fetching covers,
and `attributionText` is shown on the site.

If you ever add a source that is **not** a public first-party disclosure (for
example ReturnKoto), you must first get written permission and record it in
`data/license.json` before importing — see `docs/permission-note.md` for the
message template.

## 4. Import an export

The importer accepts **CSV, JSON or XLSX**, one file or a folder of files.
The fetcher already writes here, but a manual export works the same way.
It can read:

- a long table with columns like `Fund Name, Date, NAV, Dividend`
- a catalogue table with `Fund, AMC, Type, Shariah, Fee, Fund Size, Launch Date`
- a wide table with one fund per row and one column per date
- separate NAV and dividend files

Column names are matched automatically. You will see a plain-English mapping
before anything is written.

### Step by step (Windows PowerShell)

```powershell
# 1. Fetch from the official sources (or put a manual export in data/incoming/):
npm run data:fetch

# 2. Preview. Nothing is written in this mode.
npm run data:import -- data/incoming --dry-run

# 3. Read the "Column mapping" table it prints.
#    If a column is wrong, create data/import-map.json, for example:
#    { "nav": "NAV per unit", "date": "NAV Date" }

# 4. Import for real.
npm run data:import -- data/incoming

# 5. Validate, test and build.
npm run data:check
npm run test
npm run build
```

### What the importer will never do

- **Delete history.** It merges and appends. A date that already exists is kept
  unless the new value is identical; a conflicting value goes to review.
- **Publish a suspicious row.** A NAV move over 15% in one step, a future date,
  a zero/negative NAV, or a dividend more than 10 days from any NAV date is held
  in `data/review-needed.json`.
- **Guess a fund.** A new fund needs a name, type (`growth`/`balanced`/`income`)
  and Shariah flag (`true`/`false`). Otherwise the row waits for you.

### After an import

- `scripts/last-run.md` gets a dated changelog with the mapping and coverage.
- `data/meta.json` is refreshed.
- If `data/review-needed.json` has items, read them. When you have checked the
  rows against the source, promote them with one command:

```powershell
npm run data:approve -- --dry-run   # show what would be approved
npm run data:approve                # approve the reviewed rows
npm run data:check
```

`data:approve` only promotes rows that carry enough structured information
(fund, date, value). Anything vague stays in the review queue and is reported.

### Date and number rules

- Dates: `YYYY-MM-DD` is safest. `31/10/2026` is read **day-first**.
  `31-Oct-2026` and Excel date cells also work.
- Decimals: `1,234.50`, `৳1,234.50` and `12%` are all understood.
- One NAV per fund per date. Duplicate dates with different values go to review.

## 5. Add one fund by hand

If you only need to add a fund and its history, copy the templates:

1. Copy the sample row from `data/templates/funds.template.json` into
   `data/funds.json`, then change the values. Keep `id` and `slug` lowercase
   with hyphens and make them identical.
2. Add `data/nav/{slug}.csv` using `data/templates/nav.template.csv`.
3. Add `data/dividends/{slug}.json` using
   `data/templates/dividends.template.json` (or an empty `dividends` array).
4. Add the AMC to `data/amcs.json` if it is new.
5. Run `npm run data:check`. The build will refuse bad files and tell you which
   line to fix.

Fees are percent per year. Fund size is crore taka. Minimum investment is taka.
If you do not know a value, use `null`. The site shows “Data not available”; it
does not fill the gap with a guess.

## 6. Weekly automatic update

`.github/workflows/update-data.yml` runs every Monday at 03:17 UTC (09:17 Dhaka)
and can also be started manually from the **Actions** tab on GitHub.

What it does:

1. Installs locked dependencies and validates the committed data.
2. Checks whether the newest NAV is more than 21 days old.
3. Runs `npm run data:fetch` — fetches fresh NAV data from the official sources
   in `data/nav-sources.json`.
4. Imports `data/incoming/` (only if `data/license.json` is filled in).
5. Commits changed data with `data: NAV update YYYY-MM-DD`.
6. Opens a GitHub issue if the fetch/import fails, or if the data is three
   weeks old.

It uses the built-in `GITHUB_TOKEN`; you do not need to create a secret. The
workflow has `contents: write` and `issues: write` permission. If the licence is
not filled in, it deliberately skips the import and changes nothing.

To run it by hand: open **Actions → Update NAV data → Run workflow** on GitHub.
No secret is needed — it uses the built-in `GITHUB_TOKEN`, with `contents: write`
and `issues: write` permission.

## 7. What “stale” means

A fund with no NAV in the last **30 days** is marked **Stale** on its card, fund
page and `/data-status`, and is kept out of rankings and the calculator median.
It is not deleted. Its history still shows, with the stale warning attached.
`/data-status` lists every fund, its latest NAV date and its completeness.

## 8. Common messages and what to do

| Message | Meaning | Fix |
| --- | --- | --- |
| `data/funds.json` failed validation | A required field is missing or malformed | Read the line number in the error; compare with the template |
| `NAV must be greater than zero` | A zero/negative NAV slipped in | Correct the source file; it is not publishable |
| `New fund ... needs type and shariah columns` | The importer cannot invent a category | Add the fund to `data/nav-sources.json` with `type` and `shariah`, or add it by hand |
| `moves 18.2% in one step (over 15%)` | Possible split, bonus unit or data error | Check the AMC notice, then `npm run data:approve` and re-run `data:check` |
| `N-day NAV gap between X and Y` | The source did not publish NAVs for that period | Nothing to fix — the site shows the gap honestly on `/data-status` |
| `dividend ... is 23 days from the nearest NAV date` | The dividend date may be a record date, not a NAV date | Confirm against the source, then approve or correct |
| `Server returned 403/429 — stopping this run` | The site asked the bot to back off | Wait a day; do not retry aggressively. If it persists, email the contact in the User-Agent line |

## 9. Honesty rules the build enforces

- The site never calls a figure verified unless `data/verification.json` has a
  named checker, a date and a scope for that fund, **and** the licence allows
  verification display.
- Benchmarks marked `approximate` say so next to the number. Benchmarks marked
  `unavailable` are not drawn as if they were real.
- Rankings exclude stale funds. A fund with under 90 days of history gets no
  annualised figure. A SIP with under 12 months gets “Not enough history”.
- `npm run data:check` runs automatically before every production build. A bad
  file fails the build instead of reaching the live site.
